# What would Raffael review?

Raffael is the security reviewer on most projects ("Approved from security perspective"), and he also reviews design,
naming, tests and style closely. This skill lets anyone check a branch against his
habits before he sees it, so his review gets spent on new things.

## Evidence

The patterns are distilled from years of his code reviews, across Rails apps, a React component library and infrastructure repos. Only
habits that showed up again and again, and that make sense outside one product,
were kept.

**Maintainers only:** if a `reviews.md` sits next to this file (generated by a
local, git-ignored `sync.sh`), grep it for the verbatim threads behind a pattern
before predicting, and run `sync.sh` after he reviews a new PR. Personal notes go
in `predictions.md`, also git-ignored. Neither is needed to use the skill.

## Blockers: he insists, in bold if needed

These are flat statements, not questions. Expect "requested changes".

1. **Authorization on every endpoint, on the specific record.** (his #1 topic)
   - Every action authorizes; "authorization is never optional". Public data gets
     an explicit anonymous/guest ability, never `skip_authorization`.
     The only exceptions he has let pass are health checks and truly public
     reference data such as currencies.
   - Authorize the record, not a class or symbol: `authorize! :read_report,
     user`, not `authorize! :read, :report`. For create,
     build the record first and then authorize it. `accessible_by` alone isn't
     enough for a single record; also `authorize! :show`.
   - Every id from params is looked up through
     `Model.accessible_by(current_ability)`. Reuse the scope CanCanCan already
     loaded; "This ignores what cancancan already assigned".
     Collections use `:index` plus `accessible_by`.
   - Authorization is never conditional (`authorize! ... if x`): it leaks
     state and skips nil cases.
   - The controller authorizes and passes a pre-scoped relation into the
     service. Services don't authorize and never fall back to `.all`.
   - Abilities: use CanCanCan's own verbs (`:update`, not `:write`), and name
     actions on a subject (`:approve_expense, Report`, `:request_reset_link, User`).
     Use hash or scope conditions, not blocks, so the rule works in SQL and doesn't
     query per check. Put `cannot` rules last, and avoid `manage :all` and
     `alias_action` because they are hard to test. Use the narrowest
     subject, but don't add "fake" restrictions that a user can get around anyway.
   - Multi-tenant: never leak across tenants. Seeds, jobs and lookups run inside
     the tenant.

2. **Security hygiene.** (rarer, but always blocking)
   - Injection: no user input in raw SQL, sort columns, Elasticsearch queries,
     `constantize`, `send` or `to_sym`; use an allowlist instead.
     Never `eval`.
   - Data exposure: return 404 rather than reveal that a record exists. Don't
     reveal whether an email is registered. Don't expose fields the
     client doesn't need, and render through entities/jbuilder, never raw models.
   - Never trust client-sent amounts, statuses, types or ids.
   - Use as little `html_safe`/`dangerouslySetInnerHTML` as possible; sanitize on
     the server.
   - Secrets: never committed ("**Please rotate the token**"). Never logged:
     no response bodies, keep `filter_parameters`. Stored
     tokens are encrypted before rollout. CSP `default-src 'none'`
     with every host justified, CORS per environment, `SameSite=Strict` cookies.
   - Passwords need at least 12 characters plus complexity, enforced in the backend. No password beats a generated one.
   - The frontend enforces nothing; the backend decides.
   - He also removes security theatre: "Why do we need `SanitizedHTML` here? No
     user input?". Secure what is actually at risk.

3. **I18n for every user-facing string from the first commit.** "Please
   stop hardcoding texts" / "**never ever use hard coded texts again**".
   - Don't concatenate or split sentences; let the translation handle word order.
     Pluralize with `count`. Format dates with `I18n.l`, not `strftime`. Use
     `human_attribute_name`, not `humanize`/`capitalize`.
   - `I18n.t` in a constant or at class level is evaluated once at boot and is
     always English.
   - A shared component takes its texts as props.
   - Exception: developer-only errors and error-tracker messages stay in English,
     because translated messages break grouping.

4. **Database integrity in the schema, and no data loss.**
   - `null: false` on every boolean ("otherwise we have three states") and on
     anything that has a default. No default on a real tri-state (yes, no,
     unknown). Add foreign keys, unique indexes that match uniqueness
     validations, bigint ids, explicit decimal precision, and `jsonb`.
   - Money: always `BigDecimal`, never float, calculated in the backend.
   - Existing rows: backfill before adding a constraint. A `null: false` reference
     on a non-empty table fails in production.
   - Rename to `deprecated_*` and drop in a later cleanup. Add a new migration
     instead of editing one that has shipped. Test big migrations against a
     production dump. Rails already wraps migrations in a
     transaction.

5. **Fail loudly and atomically.**
   - Use `save!`/`update!`/`create!`/`find_by!`/`fetch`, and raise on unknown
     input instead of returning a default. "If it should never happen, raise
     so we get notified." No silent fallbacks; `0` is not `nil`.
   - Don't rescue broad errors (`NoMethodError`, `=> e`). Report to the error
     tracker with metadata; never swallow.
   - Wrap multi-step writes in a transaction. Use `with_lock` on the parent record
     where there are races. Jobs must be idempotent and safe when messages arrive
     out of order. Don't add locks or transactions that aren't needed.
   - No class-level mutable state or clients held in constants, because they break
     under threads; use an instance or `CurrentAttributes`.

## Frequent asks: usually a question, and expected to be fixed

6. **Names say exactly what the thing is and does.** (his most frequent comment)
   - The verb matches the effect: "It doesn't just fetch it, it also updates it";
     "`format_issue` doesn't format, it maps". A `?` method returns a boolean and
     has no side effects; an `!` method may raise.
   - `is*` and `?` only for booleans, plurals for collections, `_at` for
     timestamps, and units in names (`expires_in_days`). No `get_`/`set_`
     prefixes, no generic names (`Component`, `token_id`), no repeated namespace.
   - Name the domain: `saml_assertion_accepted?`, not `assertion_accepted?`. Use the vendor's own term (`instance`, not `cloud`). Use
     acronym inflections (`SAML`, `PDF`) rather than wrong casing.
   - Keep names consistent with sibling code; never rename a public API that a
     client already uses.

7. **Does this need to exist?** He asks "What is this used for?" about every
   added host, port, dependency, file, prop, column, env var, cache or config line,
   and "Why drop this?" about every removal.
   - Delete dead code, commented-out code, `console.log`/`puts`/`binding.pry`,
     unused gems and packages, and leftovers in env and deploy files.
   - Unrelated diff noise draws "Where are these changes coming from?" and "Please
     revert, it needs additional attention when reviewing."
   - Every number needs a reason that matches it ("If it's 5 minutes, why 15?"). Use named constants for magic values.
   - Caching is "the last resort". Add an index first.

8. **Tests for every new branch, written so they can fail.**
   - Ability specs cover positive and negative cases, the user themselves, and
     every role. "Please also test the reverse."
   - Cover edge and "hacking" cases: a used invite, a wrong token, an empty array,
     nil.
   - A test must be able to fail: "Is this test red if you revert the change?",
     "this will never fail". Check the precondition before the action and assert
     exact values, not values computed in the test.
   - No blanket snapshots ("nobody reviews them"); test specific properties. Don't
     mock the thing under test. Use `build` over `create` and few records, so
     tests stay fast. No VCR; mock the API instead.
   - Assertions belong in the right layer's spec. Move tests along with moved code.
     Fix test titles when behaviour changes.

9. **Reuse what already exists.** This means the repo's helper, scope,
   component, endpoint or query object; Rails or the gem (enum scopes,
   `validates ... if:`, `GraphQL.parse`, route helpers, `did_you_mean(nil)`); or
   the library already in the bundle (date-fns, not moment; axios cancellation).
   "Don't we have this already somewhere?"
   - Don't vendor libraries or monkey patch gems. Subclass and route instead of
     overriding a gem controller.
   - Use public APIs only: "It's part of the Rails internal API".
   - A new dependency must earn its maintenance and bundle size: "the less
     dependencies, the better". Use devDependencies for dev tools.
   - DRY is not absolute. He prefers explicit code when an abstraction hides
     things: "I don't like moving this into a function as it hides...".

10. **Logic in the right layer.**
    - Controllers, helpers and jobs stay thin and call a service. Business rules
      and calculations live in the backend, because mobile apps and other
      clients would otherwise have to copy them and floats break in JS.
    - A method shouldn't know its callers (SRP). Shared or base code stays generic,
      and app-specific code stays in the app.
    - An API client owns its connection, auth headers and token refresh; the caller
      owns the business query.
    - The backend doesn't know frontend routes, tabs or dropdowns; it says where a
      request came from. Formatting is a view concern.
    - Use RESTful resources: a new controller rather than a custom member action,
      `new`/`create`, DELETE to remove, GET never writes, PUT to set, PATCH to
      partially update.
    - Config comes from one central place (a settings gem or initializers), not scattered `ENV` or `process.env`.

11. **Stable, explicit API contracts.**
    - The response has the same shape on every call: a key is always present, as
      `null` when empty, and is never hidden because of state (only because of
      authorization).
    - Return raw, typed data: ISO 8601 dates, `{id, name}`, `type` plus
      `type_human`, money with its currency.
    - `snake_case` on the Ruby side. Map responses through entities or jbuilder.
    - Before changing a contract, check every consumer (mobile apps, sibling
      apps, other integrations): "Please check with the mobile team."

12. **Readable over clever.** Use guard clauses, intermediate variables, one
    argument per line with a trailing comma (smaller diffs), keyword arguments
    instead of positional booleans, and no `unless` with `&&`. Avoid hidden
    behaviour: callbacks, `delegate`, magic detection. Pass dependencies
    explicitly. Prefer a stored flag over an inferred one, e.g. a `paid_at`
    timestamp over a `paid` boolean.

13. **Formatting and lint before review.** Run prettier/rubocop before
    asking for review: "`prettier` pls", "Indention", "Newline pls :)".
    - Fix the lint warning rather than disabling it. If you must disable a rule, do
      it on one line, never for the whole file.
    - Clean up bot comments before review. Readability can beat the linter
      occasionally.

14. **Frontend.**
    - CSS: strict BEM (a modifier is not an element), class names matching the
      component, semantic modifiers (`--success`, not `--green`), colour and size
      variables (no hex), a prefix per bundle, no global rules in component files,
      `js-` hooks that are never styled, and overridable SCSS (`!default`).
    - When you change a shared style, check every place it is used.
    - React: no state derived from props; the parent owns state, and props must
      still apply after mount. Keep components dumb and composable (slots and
      children, not app-specific props). Use stable `key`s, not the array index.
      Prop types must be exact (`bool`, `node`, a real `null` rather than a noop).
      Don't render empty divs.
    - UI state lives in the URL so links can be shared. Use a
      semantic element: a button, or an anchor if middle-click should work.
    - Component library: keep old defaults, alias renamed props during a
      transition, release by tag, and keep demo assets out of the published
      package.

15. **Performance at scale.** Do the work in SQL, not Ruby loops: `pluck`,
    `exists?`, subqueries. Avoid N+1 queries (`includes`). No query on every page
    load or keystroke (debounce). Paginate, and don't pass thousands of records as
    props. Do slow or external calls in background jobs. A leading `%` search
    can't use an index.

16. **Observability.** Log why an early return or skip happened, and keep an
    `else` branch with a log line. Use tagged logging. Report to the error tracker
    with metadata, using a static title so similar errors group. Use `say` in
    migrations. Prometheus counters end in `_total`, gauges don't.

17. **Comments say why, and stay true.** He flags comments he can't follow
    ("I don't understand this comment", "Which marker?") and wrong or stale ones.
    He asks for a comment when something is surprising: an override with the
    upstream issue link, START/END markers around copied gem code, plain English
    for a cron expression, "keep in sync with X". The explanation goes **in the
    code**, not the PR thread. Every TODO carries a ticket.

18. **Scope, evidence and follow-ups.**
    - Larger refactors go to a follow-up story, and he wants the ticket linked. New
      code should still follow the better pattern from the start.
    - Small Boy Scout cleanups next to your change are welcome.
    - Security holes found in existing code get fixed now, not deferred.
    - Show that it works: screenshots or screencasts for UI, "Did you run this?",
      "Is this test red without your change?", "Did you check the other callers?"
    - Check the code against the story and the mockup. Route design questions to
      the designer or the owning team.

## Write every comment the way he would

The predicted comments are the product, so they must read like his. Rules:

- **Short.** One to three sentences. Most of his comments are under 25 words, and
  repeat nits are one or two words.
- **Ask, don't order.** Open with "Could we…?", "Can't we…?", "Don't we have…
  already?", "Why is this needed?", "What happens if…?", and often end with
  "…, no?" or "…, right?".
- **Hedge, then be concrete.** "IMHO", "I think", "Not sure, but…", "I'd…",
  "Maybe…" come first, then the exact fix. The hedge is politeness, not doubt.
- **One reason, from a failure scenario.** "Otherwise I can pass any id and read
  someone else's invoice." Not a lecture.
- **Show the code.** When the fix is small, put it in a GitHub suggestion block:

  ````
  ```suggestion
  def payment_required?(order)
  ```
  ````

  For bigger fixes, sketch it in a code block and add "(not tested)" or "please
  verify" when unsure.
- **Repeats shrink.** Second time: "ditto" or "Same here". Nits: "I18n",
  "Indention", "`prettier` pls", "Newline pls :)", "`null: false` pls", "typo", "?".
- **Emoji are light.** A 😄 or 😉 softens a nit, 🤔 marks doubt, 👍 is praise.
  At most one per comment, and none on security comments.
- **Drop the hedge only for blockers.** Security, money, data loss and hardcoded
  text get flat statements: "This should be authorized.", "Please don't commit
  credentials.", "Never use floats for money."
- **Mark what's optional.** "Nitpick:", "Up to you", "Not a blocker".
- **Praise briefly and specifically** when something is genuinely good: "Nice
  catch 👍", "Much simpler now!".

Examples of the register, by severity:

| Severity | In his voice |
|---|---|
| Blocker | This allows anyone to fetch any user's invoices. Let's use `Invoice.accessible_by(current_ability).find(params[:id])`. |
| Blocker | Never use floats for money, please use `BigDecimal`. |
| Ask | Don't we have a helper for this already? I'm pretty sure I saw it in `Formatting`... |
| Ask | IMHO this belongs into the service, not the controller? |
| Ask | What happens if `user_ids` is an empty array? 🤔 |
| Ask | If it's 5 minutes, why are we doing 15? |
| Naming | It doesn't just fetch it, it also stores it. Maybe `fetch_and_store_rates`? |
| Test | Please also test the reverse: another user shouldn't be able to do this. |
| Nit | I18n |
| Nit | `prettier` pls 😄 |
| Repeat | ditto |
| Optional | Nitpick: I'd use a guard clause here, but up to you. |

Don't overdo it. No "IMHO" in every comment, no emoji wall, no "bhai" or
nicknames, and never invent quotes and present them as things he actually said.

## How he takes replies

He accepts a reasoned reply with evidence quickly: "Okay, I see.", "Ah, makes
sense. Thanks", "Yeah, sounds legit 👍". He changes his
mind when shown a constraint. He does **not** accept:

- "smallest change that closes the review"
- "it works in testing" without the reason
- "might have changed" guesses

He then asks for an investigation or SQL output. He follows up on comments that
were ignored without a reply. He will approve to unblock others while asking for a
fix "as soon as possible".

## Predicting his review of a branch

1. Diff the branch against its base (`git merge-base` with the PR base) and read
   the diff with context.
2. Walk the diff through **Blockers** first, then **Frequent asks**. For each
   candidate, find evidence in the codebase: the sibling class that does it
   differently, the gem in the lockfile, the existing helper or scope. Check gem
   APIs in the installed source, not from memory.
3. Report the most likely first, each in this shape:

   ````
   **`app/controllers/reports_controller.rb:42`** · Blocker · authorization
   > Could we authorize the specific report here? Right now anyone with
   > `:read, Report` can pass any id, no?
   > ```suggestion
   > @report = Report.accessible_by(current_ability).find(params[:id])
   > ```
   **Fix:** load through `accessible_by`, see `InvoicesController#show`.
   ````

   The quoted part is the comment exactly as he'd write it (see "Write every
   comment the way he would"). Below it, **Fix** with the change, or **Reply**
   with a ready answer when the code is already right. Add a short "probably
   fine" list with replies.
4. Only include comments backed by evidence; 8–15 is typical. Don't pad.

The diff can be large; delegating steps 1–3 to a subagent with this file as its
lens works well.

## When Raffael has reviewed a PR

1. Map each of his comments to a pattern above and say which one it is, so the
   author sees the habit behind it, not just the single comment.
2. For each comment, give a **Fix** or a **Reply**. Use "How he takes replies" to
   judge whether a reply will land: evidence and a concrete reason, never "it
   works" or "smallest change".
3. If a comment fits no pattern, or contradicts one, say so in one line so the
   skill's maintainer can update it.
